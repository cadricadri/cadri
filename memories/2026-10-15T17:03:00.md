The hosted cluster was already designed to run on EKS in us-west-2, with staging at `staging.cadri.io` and production at `app.cadri.io`, nginx serving the web UI, and the Rust engine behind it. The open question at the start of this stretch was where TLS should end. The decision was that a network load balancer forwards TCP and nginx terminates TLS, so the load balancer never decrypts transcript bytes. A public certificate has to live on nginx. Amazon Certificate Manager certificates cannot be copied onto a pod, so they cannot be that certificate. Let's Encrypt is the public certificate authority. HTTP-01 is enough for the two hostnames, and it does not need a Gandi API token. A wildcard would. A private certificate would not be trusted by browsers or the plugin.

That decision was then built, and nothing was applied or pushed. Each environment gets its own network load balancer, because a network load balancer cannot choose a namespace from the Host header. Port 443 is passed through to nginx on 8443, since the unprivileged nginx process cannot bind 443. Port 80 reaches nginx on 8080, which answers the Let's Encrypt challenge and redirects every other path to HTTPS. cert-manager requests and renews the certificate. The challenge solver's ingress class is named `cadri-acme` and has no controller, so EKS does not create an application load balancer for it. nginx proxies `/.well-known/acme-challenge/` to that short-lived solver. When the certificate files appear, nginx reloads itself and starts TLS. The hop from nginx to the engine stays plain HTTP inside the VPC. Local Docker is unchanged: plain HTTP on port 8080 and one shared API token. Two load balancers replace the single application load balancer, and the rough monthly estimate moved from about $185–235 to about $205–260. After the first Helm install, the Gandi `staging` and `app` CNAMEs point at the two load balancer hostnames, and the certificate is issued once those names resolve.

The first container test of that nginx failed for a local reason. nginx resolves the engine hostname when it loads its config, and the test container had no host named `engine`, so it exited before listening. The retry used an IP address as the upstream. A second bug showed up in the same test: if the reload failed, the watcher remembered the new certificate hash and never tried again. The watcher now keeps the old hash until `nginx -s reload` succeeds. After that, local HTTP returned 200, port 80 redirected, the challenge path was proxied, and HTTPS came up with the strict-transport header once the certificate files appeared.

The next question was how production login actually proves who someone is. WorkOS signs the access token with its private key. The token is a JWT: the claims are readable, and the signature is the proof. The engine downloads WorkOS's public keys from `https://api.workos.com/sso/jwks/<client_id>`, caches them for at least five minutes, and checks the signature, the issuer, and the expiry locally. It does not ask WorkOS whether the token is valid on each request, and it does not decrypt the token to learn the user. The user id is `sub`. The organization id is `org_id`. The browser never puts that token in JavaScript. After AuthKit redirects back with a one-time code, the engine exchanges the code using the production API key and stores the access token and the refresh token in the `cadri_session` cookie. That cookie is HttpOnly, Secure, and encrypted with `CADRI_COOKIE_KEY`. Same-origin page requests send it automatically. The plugin cannot use the cookie. `cadri-login` stores the tokens in `~/.config/cadri/credentials.json` and later sends `Authorization: Bearer`. The engine calls WorkOS again to refresh an expired access token, to fetch a missing public key, to look up an email or organization name for the account menu, and to sign out. A revoked token still works until its expiry, because the signature check is local. Staging uses this same path with the staging WorkOS client, test API key, and `https://staging.cadri.io`. Local `./scripts/run` has no auth and one shared user. `./scripts/run-with-docker` compares one shared bearer secret and still has one shared organization.

Organization membership is also WorkOS's job. Cadri does not create organizations or inspect invitations. Self-service sign-up is off. A new user and a new organization, today, means an admin creates the organization in WorkOS and invites the email. A new user joining an existing team uses a WorkOS invitation bound to that organization. Cadri's guarantee is the signature: only WorkOS can mint a token whose `org_id` is that team, and every transcript read or write uses that claim. The request body cannot pick a different organization. There is no row for the organization until the first transcript is stored. Inside an organization there are no further permissions. WorkOS roles are not read. Someone who already has an account and wants a second team was explicitly deferred. There is no organization switcher and no Cadri rule that a user may belong to only one organization. A session token carries exactly one `org_id`, and the database is already keyed by organization and session, so a second membership later does not need a migration. A richer console of graphs and animation fits the current web UI: Vite builds static files and nginx serves them. New data needs new `/api/` routes. A live stream would be the point where the current HTTP proxy, with its 60 second timeout, is too small.

The deploy wiring was the next thing to pin down. The forty zeros in the private repo's CI workflow are a placeholder git SHA so Helm can render the chart. That job does not build or push an image. The real deploy tag is the 40-character `cadricadri/cadri` commit. GitHub does not store AWS keys, and AWS does not pull the git repos. Terraform creates an IAM role, `cadri-cloud-deploy`, that trusts GitHub Actions tokens only for `repo:cadricadri/cadri-cloud:environment:staging` and the matching production environment. The deploy workflow exchanges that token for short-lived AWS credentials, then pushes images to ECR and upgrades the cluster. The private repo still needs GitHub environments named `staging` and `production`. The public repo needs the Actions secret `CADRI_CLOUD_DISPATCH_TOKEN` so a push can trigger the private workflow. That secret is GitHub talking to GitHub.

On cost, the EKS control plane has no smaller size and no free tier. Standard support at about $73 a month is already the cheap setting. The Auto Mode fee is about $4 on a `t3.medium`, and Auto Mode will not launch anything smaller than medium. AWS Activate credits pay the invoice down. They do not change the rates. The useful cuts while pre-customer were to run staging only, stay on one node, or replace the NAT gateway with a NAT instance. A Graviton medium saves a few dollars per node and was not taken, because the node type stays Intel. Leaving EKS is the only way to remove the control-plane charge. After the credits arrived, the decision was to keep staging identical to production anyway.

`eprintln!` in the Rust engine goes to stderr. The container runs the binary directly, and `kubectl logs` shows stdout and stderr together. Following the hosted engine is `kubectl logs -n staging -l app.kubernetes.io/name=engine -f`. The unauthenticated-token warning in the core auth code does not appear on staging or production, because those pods run the WorkOS edition. The WorkOS edition's own error lines, such as a failed login exchange or a failed health check, do show up in that stream.

Before a push, `./scripts/test-rust` builds the engine workspace and runs `cargo test --workspace`, the same Rust test command as the engine CI job. It covers the core and the WorkOS edition, and it does not run formatting, Clippy, the web UI, or the plugin. `.githooks/pre-push` runs that script and stops the push on failure. This clone uses those hooks via `git config core.hooksPath .githooks`. A fresh clone needs that command once. The script was run here and 42 tests passed. A macOS linker warning about compact unwind was printed during that build and did not fail the tests.

Clippy was the last question, and it was not added to the hook. Clippy is the linter. Formatting is `rustfmt`. CI already runs `cargo fmt --all --check`, then `cargo clippy --workspace --all-targets -- -D warnings`, then the tests. Clippy with warnings denied passed locally. Formatting did not: `engine/core/src/lib.rs` disagrees with rustfmt around the TLS startup code, so the format step would fail until that file is reformatted. The recommendation was to put that same trio on the existing pre-push hook rather than on every commit, because Clippy and the tests recompile. `cargo audit` and `cargo deny` were left for CI later if they are wanted, because they need the network. They were not added.
